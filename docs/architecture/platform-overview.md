# 独立模拟平台架构

## 状态

- 决策状态：Accepted
- 起始版本：v1.0.28
- 当前正式引擎：JavaScript reference engine
- 目标正式战斗引擎：Rust core
- 浏览器目标：Rust/WASM
- 原生批处理目标：Rust CLI
- M0 行为基线：Completed

## 背景

仓库已经包含战斗模拟、Queue、刷图推荐、强化评估、生活技能规划、数据同步、角色导入和多轮结果导出。它在产品层面已经是一套平台，但计算模块仍通过源码目录、Worker 消息和共享对象隐式耦合。

长期维护需要把以下概念分开：

1. 游戏数据快照；
2. 模拟请求与结果协议；
3. 领域计算引擎；
4. 任务调度与 Worker 运行时；
5. Vue 页面、Pinia 状态和展示逻辑；
6. 外部导入、价格和数据同步适配器。

## 已拍板的架构

```text
apps/web
    ↓ versioned contracts
platform runtime / worker clients
    ↓ engine adapter
┌──────────────────────┬──────────────────────┐
│ reference-combat-js  │ rust-wasm / rust-cli │
└──────────────────────┴──────────────────────┘
    ↓
versioned game-data snapshot
```

### Vue 前端

现有 Vue 3、Pinia、Vue Router、Tailwind 和本地化体系继续保留。底层迁移不得要求重做界面，也不得让页面直接依赖 Rust 内部结构。

### JavaScript reference engine

现有 `src/combatsimulator` 在迁移期承担行为裁判：

- 保留现有公式和事件顺序；
- 支持 seeded 与显式数列随机源；
- 支持默认关闭的基础与详细战斗态轨迹；
- 通过版本化 DTO 接收请求并输出结果；
- 通过 14 组黄金场景锁定结果、随机消费和事件轨迹；
- 不承担长期高吞吐目标。

### Rust combat core

Rust 核心必须是纯领域库：

- 不引用 DOM、Vue、Pinia、Worker、网络或浏览器存储；
- 使用数值化实体标识和稳定事件序；
- 将 RNG 作为显式模拟状态，不使用全局随机函数；
- 支持完整统计与快速统计；
- 可同时编译到 WASM 和原生目标；
- 每个迁移阶段都必须和 reference engine 做差分测试。

### 强化与生活技能

当前阶段不迁移 Rust。

生活技能规划器已经以纯函数服务和较完整测试存在。强化计算是否迁移由真实基准决定，不以语言偏好决定。它们仍应逐步使用统一任务协议和游戏数据包。

### 游戏数据

`init_client_data` 提取、官方翻译同步和生成索引流程继续保留。目标是将数据提升为独立版本化快照，每次模拟结果必须能够追溯：

- 数据版本；
- 来源摘要；
- 文件哈希；
- 引擎版本；
- 协议版本。

实时市场价格属于外部输入，不属于不可变战斗数据快照。

## 目标目录

迁移完成后的目标结构如下，实施时按阶段演进，不在一个 PR 中搬迁全部源码：

```text
apps/
  web/
packages/
  contracts/
  game-data/
  platform-runtime/
  reference-combat-js/
crates/
  sim-core/
  sim-wasm/
  sim-cli/
fixtures/
  parity/
benchmarks/

```

## 不变量

1. 每个 PR 后主线必须仍可运行。
2. 默认模拟行为在迁移前后保持一致。
3. 未经版本升级，不得静默改变协议字段语义。
4. 未经差分验证，不得将新引擎设为默认。
5. UI 不得直接读取引擎内部对象或 Rust 内存布局。
6. 游戏数据与展示名称继续以 HRID 建立稳定关联。
7. 性能优化不得通过删除正常统计、降低精度或改变随机调用顺序冒充收益。
8. 未实现的 Rust 字段不得用零值或空对象伪造兼容。

## 迁移阶段

### M0：行为基线

**状态：完成。**

已完成：

- 独立仓库身份与架构文档；
- `SimulationRequestV1` 及结果、进度、错误和能力协议；
- `referenceSimulationRunner` 与旧 Worker 兼容适配器；
- native、seeded、sequence 与 tracing 随机源；
- `basic` 与 `combat` 两级事件轨迹；
- 14 组黄金请求、最终结果和完整事件轨迹；
- 场景语义断言、归档分片和 SHA-256；
- 基础、复杂、高级三层机制测试；
- reference engine 基准；
- 永久只读 CI 与生产构建验证。

当前黄金覆盖：

- 单人和三人普通区；
- 五人副本通关、团灭与重启；
- Labyrinth；
- DOT、治疗、HP/MP 恢复 Tick；
- 眩晕、致盲、沉默；
- OOM 与重新施法；
- 削弱、狂怒、诅咒；
- 反伤、反击、招架、穿透和多目标；
- Revive；
- 同时间 Buff 到期的稳定事件顺序。

### M1：Rust 基础核心

下一阶段范围：

1. 建立 Cargo workspace；
2. 创建 `sim-core`、`sim-wasm`、`sim-cli`；
3. 在 Rust 中定义协议 DTO、时间单位、ID、错误模型和 RNG trait；
4. 实现固定数列 RNG 与当前 seeded RNG 兼容实现；
5. 实现稳定事件键和最小事件队列；
6. 读取版本化 fixture，但不伪装成完整战斗引擎；
7. 建立机器可读的 Rust 自测和后续差分入口。

M1 不实现完整攻击、技能、Buff、副本、WASM 页面接入或默认引擎切换。达到基础边界后停止。

### M2：基础战斗核心

实现单位基础状态、普通攻击、命中、伤害、普通 Zone 和最小结果骨架，并接入首批简单黄金差分。

### M3：战斗功能对齐

依次迁移技能、Buff、Trigger、消耗品、控制、装备被动、Dungeon、Labyrinth 和完整统计结果。

### M4：WASM 接入

网页双引擎运行、差分诊断和逐步切换默认引擎。

### M5：统一任务运行时

统一排队、取消、进度、结果快照和导出，不强行统一各领域内部算法。

### M6：原生 CLI

高吞吐批量模拟、组合搜索和性能基准。

## 明确不做

- 不一次性重写全部功能；
- 不把第三方托管地址当作本仓库正式发布地址；
- 不把实时市场价格混入不可追溯的游戏数据快照；
- 不以最终 DPS 接近作为完整兼容性的唯一证据；
- 不在行为基线 PR 中顺手加入 Rust 半成品。

## 停止原则

每个阶段都必须：

- 主线可构建；
- reference engine 可运行；
- 已实现的 Rust 能力通过对应测试或黄金差分；
- 不用未实现字段填零来伪造兼容；
- 达到阶段成功标准后停止，不擅自扩项。

最危险的不是迁移慢，而是新引擎高速地产生看起来合理的错误结果。平台架构的工作，就是让这种错误尽可能早地难堪。
